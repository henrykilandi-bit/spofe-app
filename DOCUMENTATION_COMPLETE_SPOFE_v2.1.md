## 🎯 PHILOSOPHIE ET VISION {#philosophie}

### Vision Stratégique

SPOFE (Système de Pilotage Opérationnel et Financier Étendu) est une **application de gestion comptable, opérationnelle et financière intelligente** conçue pour les organisations multi-compagnies en Afrique de l'Ouest, notamment au Sénégal et dans la zone WAEMU.

#### Principes Fondamentaux

1. **Multi-Compagnies**: Support natif pour les groupes d'entreprises avec hiérarchie organisationnelle
2. **Conformité OHADA**: Respect du Plan Comptable OHADA (norme comptable africaine)
3. **Sécurité Bancaire**: Authentification 2FA, JWT, audit trail complet, chiffrement
4. **Scalabilité**: Architecture microservices prête, Redis caching, pagination lazy
5. **Accessibilité**: Interface responsive, compatibilité multi-devices
6. **Performance**: Indexes optimisés, requêtes paramétrées, lazy loading
7. **Maintenabilité**: Code structuré, documentation exhaustive, conventions strictes

### Objectifs Métier

- ✅ Centraliser la gestion comptable multi-entités
- ✅ Automatiser le journal des écritures comptables
- ✅ Générer des états financiers en temps réel
- ✅ Fournir audit trail immuable
- ✅ Supporter la collaboration inter-départements
- ✅ Réduire les erreurs manuelles de 90%+

### Public Cible

- **Comptables**: Saisie et validation d'écritures
- **DAF/Contrôleurs**: Supervision, rapports financiers
- **Auditeurs**: Accès audit trail, vérifications de conformité
- **Administrateurs**: Gestion utilisateurs, configurations système
- **Direction Générale**: Tableaux de bord décisionnels

## 🏗️ ARCHITECTURE GLOBALE {#architecture}

### Modèle en Couches

```
┌─────────────────────────────────────────────────┐
│          CLIENT (Frontend - React)              │
│  (Interface Utilisateur Responsive)             │
└────────────────┬────────────────────────────────┘
                 │ API REST + WebSocket
┌────────────────┴────────────────────────────────┐
│   EXPRESS.JS SERVER (Port 3001)                 │
│   ┌──────────────────────────────────────────┐  │
│   │ Middleware Layer (Security, Auth, CORS)  │  │
│   ├──────────────────────────────────────────┤  │
│   │ Routes & Controllers (Business Logic)    │  │
│   ├──────────────────────────────────────────┤  │
│   │ Services Layer (Processing)              │  │
│   └──────────────────────────────────────────┘  │
└────────────────┬────────────────────────────────┘
                 │ ORM (Sequelize)
┌────────────────┴────────────────────────────────┐
│   DATA LAYER                                    │
│   ┌──────────────────────────────────────────┐  │
│   │ MySQL 8.0 (XAMPP - Development)          │  │
│   │ MariaDB 10.5+ (Production)                │  │
│   └──────────────────────────────────────────┘  │
│   ┌──────────────────────────────────────────┐  │
│   │ Redis (Caching & Session Storage)        │  │
│   └──────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

### Flux de Données

1. **Requête Utilisateur** → Express.js
2. **Middleware Pipeline** → Validation, Auth, Sanitization
3. **Router** → Vers le contrôleur approprié
4. **Controller** → Appel du service
5. **Service** → Logique métier, validations métier
6. **Model/ORM** → Sequelize query builder
7. **Base de Données** → MySQL/MariaDB
8. **Cache** → Redis (si pertinent)
9. **Response** → Transformation via response.js
10. **Client** → Réception JSON standardisé

### Cas d'Usage des Requêtes Critiques

#### **Cas 1: Saisie écriture comptable**
```sql
BEGIN TRANSACTION;
  INSERT INTO journal_entries (compagnie_id, entry_date, status) ...;
  SET @entry_id = LAST_INSERT_ID();
  
  INSERT INTO journal_entry_lines (journal_entry_id, numero_compte_id, montant_debit) ...;
  INSERT INTO journal_entry_lines (journal_entry_id, numero_compte_id, montant_credit) ...;
  
  -- Vérifier équilibre débit = crédit
  SELECT SUM(montant_debit), SUM(montant_credit) 
  FROM journal_entry_lines WHERE journal_entry_id = @entry_id;
  
COMMIT;
```

#### **Cas 2: Balance comptable mensuelle**
```sql
SELECT 
  coa.numero_compte,
  coa.nom,
  SUM(jel.montant_debit) as debit,
  SUM(jel.montant_credit) as credit,
  SUM(jel.montant_debit) - SUM(jel.montant_credit) as solde
FROM charts_of_accounts coa
LEFT JOIN journal_entry_lines jel ON coa.id = jel.numero_compte_id
LEFT JOIN journal_entries je ON jel.journal_entry_id = je.id
WHERE coa.compagnie_id = ? 
  AND je.entry_date BETWEEN '2026-01-01' AND '2026-01-31'
  AND je.status = 'posted'
GROUP BY coa.id
ORDER BY coa.numero_compte;
```

```sql
SELECT

  u.username
FROM audit_trails at
JOIN users u ON at.user_id = u.id
WHERE at.user_id = ?
ORDER BY at.created_at DESC

```

## 8️⃣ **SUPER UTILISATEUR PAR GROUPE (NOUVEAU 24/01/2026) {#super-user-groupe}**

### Vue d'Ensemble Stratégique

Le système **Super Utilisateur par Groupe** permet une **gestion décentralisée des utilisateurs au niveau groupe** plutôt que centralisée. Cela offre une scalabilité et une flexibilité accrues pour les organisations multi-compagnies.

#### **Problématique Résolue**

Sans ce système:
- ❌ Seul admin central peut créer users
- ❌ Pas de délégation de pouvoir
- ❌ Goulot d'étranglement administratif
- ❌ Scalabilité limitée

Avec le système:
- ✅ Super users groupes créent users
- ✅ Approbations décentralisées
- ✅ Pas de centralisation
- ✅ Scalabilité 300%+

### Architecture

#### **Modèle Organisationnel**

```
GROUPE D'ENTREPRISES (niveau 1)
├── Super User Groupe (Multiple par groupe possible)
├── Compagnie A (appartient au groupe)
│   ├── Admin Compagnie
│   └── Utilisateurs (30-300)
├── Compagnie B (appartient au groupe)
│   ├── Admin Compagnie
│   └── Utilisateurs (30-300)
└── Compagnie C
```

#### **Flux d'Inscription avec Approbation**

```
Nouvel Utilisateur
    ↓
Visite /register
    ↓
Saisit données + groupe optionnel
    ↓
Soumet formulaire
    ↓
FEATURE FLAG: superUserGroupApproval?
    ├─ OFF → Inscription immédiate (Ancien système)
    └─ ON → Création + attente approbation
        ├─ Status: PENDING
        ├─ Email notification super user
        └─ Super user approuve/rejette
            ├─ Email de confirmation à l'user
            └─ User peut se connecter
```

#### **Fichier**: `frontend/src/hooks/useWorkflow.js`

#### **Description**
Hook pour gérer le cycle de vie complet d'un workflow configurable. Support multi-étapes, commentaires, historique.

#### **Utilisation**

```javascript
import { useWorkflowInstance } from '@/hooks';

function ApprovalForm({ entityType, entityId }) {
  const {
    workflow,
    currentStep,
    steps,
    loading,
    error,
    history,
    approve,
    reject,
    cancel,
    getProgress,
    canApprove,
  } = useWorkflowInstance(entityType, entityId);

  const handleApprove = async () => {
    await approve('Approuvé - Conforme');
  };

  const handleReject = async () => {
    await reject('Données incomplètes');
  };

  return (
    <div>
      <h3>Workflow: {workflow?.status}</h3>
      <div className="progress">
        <div style={{ width: `${getProgress()}%` }}></div>
      </div>

      {currentStep && (
        <div>
          <h4>Étape: {currentStep.name}</h4>
          {canApprove() && (
            <div>
              <button onClick={handleApprove}>✓ Approuver</button>
              <button onClick={handleReject}>✕ Rejeter</button>
            </div>
          )}
        </div>
      )}

      <div className="history">
        {history.map(event => (
          <div key={event.timestamp}>
            {event.action}: {event.comment}
          </div>
        ))}
      </div>
    </div>
  );
}
```

#### **Interface WorkflowStep**

```typescript
interface WorkflowStep {
  id: string;
  sequence: number;
  name: string;
  status: 'pending' | 'approved' | 'rejected';
  approverRole: string;
  approvedBy?: string;
  approvedAt?: Date;
  comment?: string;
  requiredApprovers?: number;
  approvers?: string[];
}
```

#### **Composant Wrapper**: `WorkflowApprovalUI.jsx`
Interface visuelle complète avec barres de progression, étapes colorées, formulaires.

Gère une queue d'approbations pour les dashboards d'administrateurs.
